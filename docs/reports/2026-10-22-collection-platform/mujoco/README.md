# MuJoCo 采集后端开发记录

范围为独立采集场景的双臂、双手真实动力学跟随；不修改方向键任务，不连接采集台。L1、L2 由统一验收程序执行，本页的短测不能替代验收。

## 实现与依据

`CollectionMujocoBackend` 组合 v4.4 的双侧 AR5 与手部 URDF，保留手柄根部固定、桌面和碰撞箱体的位置与尺寸。没有采用 K0 报告中架高或倾斜的试验建议；K0 未获得完整握持证书与本轮参考轨迹采集是不同结论。右手直接使用配置引用的 L25/right 对应资产，不以左手几何镜像替换；安装偏移由共享采集场景标记 `assumed`。

位置执行器、关节等式和碰撞位掩码按 [MuJoCo XML 原始文档](https://mujoco.readthedocs.io/en/stable/XMLreference.html) 与 [建模文档](https://mujoco.readthedocs.io/en/stable/modeling.html) 组合。适配现有固定任务的同一 inertia 投影函数，仅修正源惯量的三角不等式违规，并记录派生前后数值。左右机器人内部碰撞分别关闭，保留两侧之间、机器人与手柄及支撑的碰撞。mimic 使用原生 joint equality，左拇指比例 1.02，右侧 1.03，四指 DIP 比例 0.89。

新采集后端统一沿用现有 SAPIEN 的占位驱动值：手部 kp=240、kv=8、力矩上限 60、armature=0.0001；臂部 kp=20000、kv=2000、力矩上限 500、armature=0.01。这些值未经过硬件辨识，与既有方向键任务的驱动选择不同；没有修改后者。MuJoCo 使用原生 body gravity compensation；SAPIEN 被动力补偿还包含科氏项，这是需要实测比较的模型差异，不能预先归为坐标错误。原生手柄采用资源自带数值策略及 0.5 ms 物理步长，不以额外状态投影改变接触。

命令只写机器人 actuator ctrl。qpos 仅在 reset 初始化时设置；每次跟随后，手柄信号和关节位移从公开 handle 读取，掌根和指尖从求解后的 body world pose 读取。指尖定义复用共享 schema helper。观测中的 robot_contact 表示上一控制区间任一原生接触中包含机器人且接触距离非正。渲染为可选的 MuJoCo RGB 接口；渲染帧率必须实际测量。

## 可检验假设与最小验证

假设一：同一 URDF、安装矩阵和 schema 指尖定义下，两个后端无接触时的位姿差主要来自关节跟随误差。验证时先用相同初始关节姿态比较 FK，再以相同动态命令比较实际关节及世界位姿，分别报告误差；若静态 FK 已显著不同，则优先推翻动力学解释，检查根姿态、关节零位与 mesh 偏移。

假设二：本后端通过动力学执行器跟随，而非回写目标到观测。最小短测改变双臂和双手目标，比较 apply 前后及逐物理步的实际 qpos；apply 后尚未 step 时应不变，step 后应出现连续跟随。再检查手柄信号是否始终等于实际手柄关节通过公开编码器的结果。该短测不证明接触操控成功。

## 执行记录

实现已写入；L1、L2、渲染速度当前均未完成测量。依赖安装、正式门槛和执行许可由主代理统一管理。运行前实际检查四张 GPU 都忙，后续设置 CUDA_VISIBLE_DEVICES 为空，物理和 EGL/Mesa 图像均使用 CPU。

首次短测已成功编译完整场景，随后在首次观测触发共享 schema 的类型错误：`pose_to_matrix` 仅接受 list/tuple，helper 原传入 ndarray。主代理已将共享 helper 改为显式 `.tolist()`；属于共享修复预算第 1 次，本后端未通过改物理参数绕过问题。修复后短测通过：

| 项目 | 实测 |
|---|---:|
| 仿真时长 | 0.10000000000000007 s |
| 该段动力学墙钟时间 | 0.0622001 s |
| 相对初态手关节最大变化 | 0.00980040 rad |
| 相对初态臂关节最大变化 | 0.00630062 rad |
| 最后控制区间 robot_contact | false |
| 图像形状 | 480×640×3 |
| 首帧耗时，包含渲染器初始化 | 2.99243 s |
| nq / nv / nu | 76 / 76 / 66 |

`apply` 后未步进时 qpos 严格不变、步进后观测有限及维度正确、渲染副本状态同步均通过断言。运行库是 MuJoCo `3.16.0+concon.sdf3689.2`、手柄包 `0.4.0`。0.1 s 短测没有覆盖长时接触、L1 或 L2；上述位移是对小目标变化的响应，不是跟随误差或门槛结果。

渲染诊断第 1 次：独立测速脚本先导入 OpenGL.GL，再导入 MuJoCo，EGL 初始化失败；此前先由 MuJoCo 初始化的首帧成功。最小对照只增加 `PYOPENGL_PLATFORM=egl`，保持场景、软件渲染器和物理设置不变。对照成功，支持导入时 OpenGL 平台选择不匹配的解释。实际渲染器为 `llvmpipe (LLVM 15.0.7, 256 bits)`；首帧后静态场景 10 帧耗时 19.6667155 s，即 **0.508473 fps**。该值未含物理推进、图像编码或网络传输，不能当作端到端推流帧率，也不满足实时显示。没有通过减模型、改接触或占用忙 GPU 获得更高数值。

时钟接口修复第 1 次：主代理指出原数据是 30 Hz，单次控制区间不是 0.5 ms 的整数倍。改为累计请求时间并在累计物理 tick 上取整，实际仿真时间仍来自 data.time，避免逐帧取整产生时钟漂移。三次 1/30 s 的无渲染短测通过：实际时间依次为 0.0335000、0.0665000、0.1000000 s，最大采样时差 0.166667 ms；总动力学墙钟 0.0591065 s，确认没有初始化 Renderer。

后端修复第 2 次：主代理授权接触布尔量的短路优化。原实现每个原生子步都遍历全部接触，即使该控制区间已经确认机器人接触仍继续遍历。现仅在区间布尔量为 false 时扫描，找到首个 `dist <= 0` 且包含机器人 body 的接触后立即停止扫描，该区间其余原生子步只继续动力学。每个控制区间仍重新置 false，随后对所有子步作同样的布尔 OR；原生 `mj_step` 次数、SDF、迭代数、碰撞组、控制器及全部物理数值不变。此优化尚未完成基线对照，不能预先声称它解释或解决了真实回放的慢速。为保留正在运行的基线，仅修改本地代码，未替换其远端源码，也未启动新的计算。

## 原生 CPU 工作线程短测

主代理随后授权唯一一组 8-worker 原生线程池实验，范围限定为原 8 月输入的首 0.5 s，不构成 L1 或 L2。依据是 [MuJoCo 原始线程 API](https://mujoco.readthedocs.io/en/stable/APIreference/APIfunctions.html#mju-threadpool)，`mju_threadpool(data, 8)` 为该 data 创建 8 个 worker；[原始仿真文档](https://mujoco.readthedocs.io/en/stable/programming/simulation.html#multi-threading) 说明引擎内的并行机制。GPU 禁用、BLAS/OpenMP/MKL/NumExpr 线程均保持 1，未改变求解器、SDF、增益、时间步、碰撞组或输入流。

可检验假设是：原生碰撞/约束并行能够减小相同控制区间的耗时，而输出仍与既有单 worker 基线一致或在明确量化的浮点误差内。专属脚本 `compare_native_threads.py` 固定只执行 15 个 30 Hz 控制区间，对比既有 `cpu-threads-1` 首 15 行，输出关节角、掌根及指尖位置和姿态的中位数/P95/最大差，接触布尔量差异、时间戳差异和墙钟耗时。若没有提速或观测显著改变，不将其用于门槛回放。

该对比的旧基线还未使用接触扫描短路，而实验代码包含该语义等价优化，因此观察到的墙钟比值不能全部单独归因于原生工作线程；先前短路对照仍慢的观察只能作为辅助证据。唯一短测现已完成：

| 项目 | 结果 |
|---|---:|
| 原输入/控制行 | 0.5 s / 15 |
| 8-worker 墙钟 | 22.1367 s |
| 其中动力学步进墙钟 | 22.0969 s |
| 旧单线程基线首 15 行墙钟 | 36.4591 s |
| 两次墙钟比值 | 1.647× |
| 手及臂关节差，中位/P95/最大 | 0 / 0 / 0 rad |
| 掌根及指尖位置差，中位/P95/最大 | 0 / 0 / 0 m |
| 接触行 / 布尔量不一致 | 14 / 0 |
| 时间戳最大差 / 解码错误 | 0 s / 0 |

掌根和指尖的完整位姿原数组逐值完全相同。脚本的 acos 姿态角计算因单位四元数浮点范数得到至多 8.94e-8 rad 的自比较残差，不能将其解释为运动差异。8-worker 仍需约 44.3 s 墙钟推进 1 s 仿真，不能称实时，也不足以证明长时吞吐或确定唯一瓶颈。未为此修改后端默认值或共享 CLI，未扫描其他线程数。

## 用户裁决 2：无环境碰撞变体

用户后续裁决允许 L1/L2 使用无环境碰撞代码变体：v4.4 场景文件不变，通过独立构造参数 `environment_collisions=False` 将桌面、手柄、立柱及其他固定物全部 geom 的 contype/conaffinity 置零。机器人原有的左右组、安装、驱动及内部自碰策略完整保留；默认 `True` 仍构建原完整场景。该变体明确用于无环境碰撞的跟随/坐标一致性验收，不能作为物理接触操控成功的证据。

接触分类统一调用共享 `has_robot_contact`，只把机器人相关且原生几何距离非正的接触纳入控制区间 OR；不把 margin 内的正距离候选或单独的预解算冲量算作穿透接触。环境开关会记入会话 meta，不能只凭同一场景文件哈希把两个变体当作相同物理配置。

原 8 月流 1 s CPU 无环境碰撞短测通过：30 行实际时间 0.9999999999999453 s，墙钟 0.376620 s，解码错误 0，robot_contact 行数 0；28 个环境 geom 双掩码均为零，124 个机器人 geom 保留原有 contype 集合 `{0,2,4}`，没有初始化 Renderer。该步骤只核对开关、schema、时间和解码，不自行启动 L1/L2；此前完整场景记录保留，不能以新变体覆盖其慢速或接触差异。

修复预算：加载/短驱动步骤最多 3 次修复，每次发现、改动与复测结果追加本页。
